# Candidate Notes - UDA-Hub

## Project Overview

UDA-Hub is a LangGraph-powered multi-agent decision system for customer support automation, built for CultPass - a cultural experience subscription platform. The system processes support tickets through a pipeline of specialized agents: classification, knowledge-base resolution, and escalation.

## Architecture

**Agent Graph (4 agents, 5 nodes, 6 edges):**

```txt
START → supervisor_node → classifier_agent → resolver_agent
    → (conditional) confidence >= 0.6 → supervisor_final_node → END
    → (conditional) confidence < 0.6 → escalation_agent → supervisor_final_node → END
```

### Agents

- **SupervisorAgent** (`supervisor_node` / `supervisor_final_node`): Entry/exit point. Loads long-term memory via `memory_tool` MCP server at start, writes memory on completion.
- **ClassifierAgent**: Reads ticket text and assigns category (`billing`, `account`, `technical`, `subscription`, `content`, `onboarding`), urgency, and routing label using LLM structured output.
- **ResolverAgent**: Performs RAG via `kb_search` MCP tool (keyword/tag matching against 18 Knowledge Base articles). Uses LLM to generate response and compute confidence (0.0–1.0). Threshold: >= 0.6 resolves, < 0.6 escalates.
- **EscalationAgent**: Generates structured escalation summary with reason, priority, customer context, and suggested actions.

### MCP Tools (FastMCP)

- **account_lookup**: Queries CultPass external DB for user profile + subscription data; cross-references UDA-Hub for open tickets.
- **refund_tool**: Validates ticket, processes refund, logs to RefundAction table.
- **kb_search**: Searches Knowledge table via keyword/tag/content matching with minimum score threshold (>= 4). Used by ResolverAgent via `langchain-mcp-adapters`.
- **read_memory / write_memory**: Reads/writes ConversationMemory records. Used by SupervisorAgent via `langchain-mcp-adapters`.

### MCP Adapter Integration

All agents access MCP tools via `langchain-mcp-adapters` (`load_mcp_tools`), which loads tools from FastMCP servers as LangChain-compatible tool objects. No direct SQLAlchemy calls exist inside agent files — all database access goes through FastMCP tool servers.

## Knowledge Base

18 articles across 6 categories:

- **Billing & refunds** (3): Refund request, billing cycle, double charge dispute
- **Account management** (3): Login/password reset, email update, account deletion
- **Technical troubleshooting** (3): App crashes, QR code scanning, video streaming
- **Subscription plans** (3): Cancel/pause, upgrade, downgrade
- **Content & features** (2): Rating system, leaving reviews
- **Onboarding** (2): Getting started, app download/setup

## Memory

- **Short-term**: LangGraph `MemorySaver` checkpointer, scoped to `thread_id` (ticket ID).
- **Long-term**: `ConversationMemory` table in UDA-Hub DB. Written on resolution/escalation via `memory_tool` MCP server. Retrieved at session start via category + keyword matching. Schema: `{memory_id, account_id, ticket_id, summary, category, resolution_type}`.

## Key Design Decisions

1. **No langgraph-supervisor**: Graph built entirely with raw `StateGraph`, `add_node`, `add_edge`, `add_conditional_edges`.
2. **Keyword-based RAG**: Uses SQL LIKE + tag/content matching with minimum score threshold (>= 4) to ensure relevance. No external vector DB dependency.
3. **DB-based long-term memory**: Same SQLite DB as UDA-Hub core - self-contained, no external services.
4. **Confidence via LLM**: The resolver agent's prompt asks the LLM to evaluate article relevance, completeness, and specificity before assigning confidence.
5. **All tools through FastMCP**: No direct SQLAlchemy in agent files. All DB access via `FastMCP` tool servers loaded via `langchain-mcp-adapters`.

## Edge Cases Handled

- Empty/malformed input → defaults to `unknown` category, escalation routing
- Missing user in external DB → returns `{error: "User not found"}`
- Closed tickets → refund tool rejects with `{error: "Ticket already closed"}`
- Negative refund amounts → validation error
- No KB match → confidence 0.0 → escalation triggered
- Memory retrieval with no prior history → empty `memory_context`
- LLM failure → fallback to `unknown` category with escalation routing
