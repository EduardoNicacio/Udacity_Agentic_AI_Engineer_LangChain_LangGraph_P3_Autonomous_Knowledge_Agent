# Candidate Notes - UDA-Hub

## Project Overview

UDA-Hub is a LangGraph-powered multi-agent decision system for customer support automation, built for CultPass - a cultural experience subscription platform. The system processes support tickets through a pipeline of specialized agents: classification, support tool invocation, knowledge-base resolution, and escalation.

## Architecture

**Agent Graph (5 agents, 7 nodes, 7 edges):**

```txt
START → supervisor_node → classifier_agent → route_by_label()
    → routing_label='resolver' → support_tools_node → resolver_agent
        → (conditional) confidence >= 0.6 → supervisor_final_node → END
        → (conditional) confidence < 0.6 → escalation_agent → supervisor_final_node → END
    → routing_label='escalation' → escalation_agent → supervisor_final_node → END
```

**Agent trace examples:**

- Resolved: `supervisor_node -> classifier_node -> support_tools_node -> resolver_node -> supervisor_final_node`
- Escalated: `supervisor_node -> classifier_node -> escalation_node -> supervisor_final_node`

### Agents

- **SupervisorAgent** (`supervisor_node` / `supervisor_final_node`): Entry/exit point. Loads customer-scoped long-term memory via `memory_tool` MCP server at start, writes memory on completion.
- **ClassifierAgent**: Reads ticket text and assigns category (`billing`, `account`, `technical`, `subscription`, `content`, `onboarding`), urgency, and routing label using LLM structured output. Logs classification decision.
- **SupportToolsAgent**: Invokes `account_lookup` (for billing/account tickets) and `process_refund` (for refund requests) MCP tools based on classification. Records tool results in state.
- **ResolverAgent**: Performs RAG via `kb_search` MCP tool (keyword/tag/content matching with stemming and phrase matching against 18 Knowledge Base articles). Uses LLM to generate response and compute confidence (0.0-1.0). Threshold: >= 0.6 resolves, < 0.6 escalates.
- **EscalationAgent**: Generates structured escalation summary with reason, priority, customer context, and suggested actions.

### MCP Tools (FastMCP)

- **account_lookup**: Queries CultPass external DB for user profile + subscription data; cross-references UDA-Hub for open tickets. Invoked by SupportToolsAgent for billing/account tickets.
- **refund_tool**: Validates ticket, processes refund, logs to RefundAction table. Invoked by SupportToolsAgent for refund-related tickets.
- **kb_search**: Searches Knowledge table via keyword/tag/content matching with stemming, phrase matching, and category alignment. Min score threshold >= 6. Used by ResolverAgent via `langchain-mcp-adapters`.
- **read_memory / write_memory**: Reads/writes ConversationMemory records, scoped by customer_id. Used by SupervisorAgent via `langchain-mcp-adapters`.

### MCP Adapter Integration

All agents access MCP tools via `langchain-mcp-adapters` (`MultiServerMCPClient` + `StdioConnection`), which loads tools from FastMCP servers as LangChain-compatible tool objects. A direct-import fallback (`direct_tools.py`) is used when MCP subprocess spawning fails (e.g., in Jupyter notebooks where `io.UnsupportedOperation: fileno` prevents `subprocess.Popen` stderr handles). No direct SQLAlchemy calls exist inside agent files - all database access goes through FastMCP tool servers.

## Knowledge Base

18 articles across 6 categories:

- **Billing & refunds** (3): Refund request, billing cycle, double charge dispute
- **Account management** (3): Login/password reset, email update, account deletion
- **Technical troubleshooting** (3): App crashes, QR code scanning, video streaming
- **Subscription plans** (3): Cancel/pause, upgrade, downgrade
- **Content & features** (2): Rating system, leaving reviews
- **Onboarding** (2): Getting started, app download/setup

## Memory

- **Short-term**: LangGraph `MemorySaver` checkpointer, scoped to `thread_id` (ticket ID). Supports multi-turn conversations with append-only message history via `operator.add`.
- **Long-term**: `ConversationMemory` table in UDA-Hub DB. Written on resolution/escalation via `memory_tool` MCP server. Retrieved at session start via category + keyword matching. **Customer-scoped** via `customer_id` field (= user_email).

## Key Design Decisions

1. **No langgraph-supervisor**: Graph built entirely with raw `StateGraph`, `add_node`, `add_edge`, `add_conditional_edges`.
2. **Classifier routing**: After classification, tickets with routing_label='escalation' skip support_tools and resolver, going directly to escalation. This ensures high-priority issues reach escalation immediately. Resolver-path tickets go through support_tools_node first, which invokes account_lookup (billing/account) or process_refund (refund requests) before the resolver performs KB search.
3. **Improved KB search ranking**: Uses stemming, phrase matching, weighted scoring (tag=4, title=5, content=2, phrase=8-10), and category alignment to ensure correct articles surface first.
4. **Customer-scoped memory**: All long-term memory reads/writes are filtered by customer_id, ensuring each customer's history is isolated.
5. **Support tools in workflow**: account_lookup and refund MCP tools are invoked during the workflow (not just available), with results recorded in state.
6. **Confidence via LLM**: The resolver agent's prompt asks the LLM to evaluate article relevance, completeness, and specificity before assigning confidence.
7. **All tools through FastMCP**: No direct SQLAlchemy in agent files. All DB access via `FastMCP` tool servers loaded via `langchain-mcp-adapters`.

## Edge Cases Handled

- Empty/malformed input -> defaults to `unknown` category, escalation routing
- Missing user in external DB -> returns `{error: "User not found"}`
- Closed tickets -> refund tool rejects with `{error: "Ticket already closed"}`
- Negative refund amounts -> validation error
- No KB match -> confidence 0.0 -> escalation triggered
- Memory retrieval with no prior history -> empty `memory_context`
- LLM failure -> fallback to `unknown` category with escalation routing
- Support tools unavailable -> graceful degradation, workflow continues
